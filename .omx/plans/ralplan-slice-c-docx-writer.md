# RALPLAN Slice C — Adapter Selection + MVP DOCX Writer Productization

## Requirements Summary

Create a library-only Slice C that chooses the DOCX adapter and productizes an MVP DOCX writer without entering UI, store, Tauri, or desktop save flow. Slice B evidence is non-binding but sufficient for adapter selection: `ts-docx` and `openxml-sidecar` both produced `warn` with `0` validation errors, while `ts-docx` has lower runtime cost and lower packaging burden than `openxml-sidecar` (`experiments/docx-adapter-comparison/reports/summary.json`). The user authorized a product dependency if necessary, forbids a manual-template route, and forbids high-fidelity/Word-openability promises.

## Evidence Snapshot

- `src/lib/docx-export-contract.ts` defines the export contract and already embeds boundaries `docx-only`, `no-high-fidelity-replica`, and `no-template-file` in `buildDocxExportContract`.
- `src/lib/docx-intermediate.ts` defines the renderer-neutral MVP block set: `documentTitle`, `heading`, `paragraph`, `list`, and `table`.
- `src/lib/docx-match-review.ts` defines `DocxAdapterResultLike` and maps adapter `validationErrors` to blocking review failures and `knownWarnings` to non-blocking warnings.
- `src/lib/docx-export-record.ts` already records adapter id, output metadata, review verdict, status, and diagnostics.
- `src/test-helpers/docx-export-fixtures.ts` provides the Chinese formal-document fixture and format-profile rules for tests.
- `experiments/docx-adapter-comparison/package.json` used `docx` `^9.6.1`; root `package.json` does not yet include `docx` or `jszip`.
- App compilation targets browser-compatible `ES2020` + `DOM` libs in `tsconfig.app.json`, so product writer boundaries should use `Uint8Array`/`ArrayBuffer`/`Blob`, not Node `Buffer`.

## RALPLAN-DR Summary

### Principles

1. **Library-only Slice C:** no UI, store, Tauri commands, filesystem save flow, or desktop integration.
2. **Evidence-bounded MVP:** choose the adapter using Slice B structural evidence, but keep warnings for untested guarantees.
3. **No template/high-fidelity route:** no source DOCX/template input, no copied style XML, no exact pagination/visual-replica promise.
4. **Auditable pipeline reuse:** preserve the existing contract → intermediate → adapter → review → record chain.
5. **Browser-safe product dependency:** isolate third-party DOCX/ZIP dependencies behind `src/lib` adapters and prove Vite bundling.

### Decision Drivers

1. **Runtime/packaging cost:** `ts-docx` has low runtime cost and medium packaging risk; `openxml-sidecar` has high runtime and packaging risk.
2. **MVP scope fit:** product lib writer can render existing intermediate blocks without sidecar packaging or Tauri work.
3. **Validation honesty:** generated bytes must be structurally probed and warnings must preserve unsupported manual-openability/high-fidelity limits.

### Options Considered

#### Option A — Choose `docx` npm / `ts-docx` MVP adapter (recommended)

- Pros: lowest runtime cost; fits browser/Vite library implementation; aligns with existing intermediate block set; avoids sidecar packaging; can be isolated in one adapter module.
- Cons: does not prove manual Word openability or high-fidelity style replica; needs explicit structural package probing to avoid trusting adapter self-reporting.

#### Option B — Choose OpenXML sidecar

- Pros: stronger low-level OpenXML control; likely easier to evolve toward advanced package validation.
- Cons: Slice B reports high packaging and runtime cost; introduces sidecar distribution/runtime work outside Slice C library-only scope; no better validation-error result than `ts-docx` for MVP fixture.

#### Option C — Defer product adapter / keep experiments only

- Pros: avoids adding product dependency before manual Word testing.
- Cons: blocks Slice C productization despite existing warn/0 evidence and already-built contract/intermediate/review/record layers.

#### Invalidated Alternative — Manual template route

- Rejected because the user explicitly forbids it and the contract already includes `no-template-file`; it would also imply fidelity expectations Slice C is not allowed to promise.

## ADR — Slice C Adapter Selection

**ADR target:** include this ADR section in `.omx/plans/ralplan-slice-c-docx-writer.md`. If the execution lane wants a standalone record, copy it unchanged to `.omx/plans/adr-docx-slice-c-adapter-selection.md`.

### Decision

Choose the product `docx` npm package (`ts-docx` adapter, stable adapter id `docx-npm.v1`) for Slice C MVP DOCX generation.

### Drivers

- Slice B showed both candidates reached `warn` and `0` validation errors.
- `ts-docx` had low runtime cost and medium packaging risk; `openxml-sidecar` had high runtime and high packaging risk.
- Slice C is limited to product library code and tests, not UI/store/Tauri/sidecar packaging.

### Alternatives Considered

- **OpenXML sidecar:** rejected for MVP because its packaging/runtime cost is high and its sidecar distribution concerns belong outside Slice C.
- **Manual template/imported DOCX styles:** rejected by user constraint and existing contract boundary.
- **No adapter selection:** rejected because Slice C’s goal is product writer productization, and Slice B produced enough non-blocking evidence to choose an MVP adapter.

### Why Chosen

`docx` npm provides the shortest product path from the existing intermediate document to browser-safe DOCX bytes while preserving auditable review/record behavior. Its limitations are acceptable only if Slice C makes structural probing mandatory and carries known warnings for unsupported manual Word openability/high-fidelity claims.

### Consequences

- Add root runtime dependencies: `docx` and a browser-compatible ZIP probe dependency if needed for product validation (`jszip` is acceptable as runtime dependency if used by `src/lib/docx-package-probe.ts`).
- Keep `docx` imports isolated to `src/lib/docx-ts-adapter.ts`.
- Keep ZIP/probe imports isolated to `src/lib/docx-package-probe.ts`.
- Do not alter `docx-export-contract`, `docx-intermediate`, `docx-match-review`, or `docx-export-record` unless execution discovers a small type extension is strictly necessary.

### Follow-ups

- Later Slice D or UI slice can wire a save/export button through store/Tauri.
- Later fidelity work can add explicit Word/manual-openability validation, but must not be implied by Slice C.
- Later adapters can implement the same adapter boundary if OpenXML sidecar becomes necessary.

## Recommended File Changes

### Add

1. `src/lib/docx-ts-adapter.ts`
   - Owns all `docx` package imports.
   - Exports `DOCX_NPM_ADAPTER_ID = "docx-npm.v1"`.
   - Exports a browser-safe render function, e.g. `renderDocxWithTsAdapter(input)`.
   - Converts `DocxIntermediateDocument` blocks to simple DOCX title/heading/paragraph/list/table constructs.
   - Uses browser-safe generation (`Packer.toBlob` or `Packer.toArrayBuffer`), not `Packer.toBuffer`.
   - Returns `{ adapterId, bytes, sizeBytes, validationErrors, knownWarnings, outputPath? }`; omit `outputPath` unless a real caller-provided write path exists later.
   - Emits stable warnings for `manual-word-openability-not-tested` and `high-fidelity-style-replica-not-supported`.

2. `src/lib/docx-package-probe.ts`
   - Product runtime structural probe, not test-only scaffolding.
   - Accepts `Uint8Array | ArrayBuffer | Blob`.
   - Returns normalized `{ validationErrors: string[]; knownWarnings: string[]; packageParts?: string[]; structuralAssertions?: ... }`.
   - Minimum blocking checks: non-empty bytes, ZIP/package readable, `[Content_Types].xml`, `_rels/.rels`, `word/document.xml`, and detectable document XML content.
   - Minimum warning checks: no manual Word openability performed; no high-fidelity replica assertion.
   - If it imports a ZIP parser such as `jszip`, add that dependency to root `package.json` as a runtime dependency, not dev-only.

3. `src/lib/docx-writer.ts`
   - Orchestrates `buildDocxExportContract`, `buildDocxIntermediateDocument`, `renderDocxWithTsAdapter`, `probeDocxPackage`, `reviewDocxExport`, and `buildDocxExportRecord`.
   - Exports a product API such as `writeDocxExport(input)` returning `{ contract, intermediate, adapterResult, review, record, bytes }`.
   - Merges adapter/probe validation errors and warnings before review.
   - Does not write files, call Tauri commands, update stores, or reference UI code.

4. `src/lib/docx-ts-adapter.test.ts`
   - Tests byte generation, adapter id, browser-safe bytes, block rendering coverage, warning propagation, and no Node-only imports/behavior.

5. `src/lib/docx-package-probe.test.ts`
   - Tests valid generated package detection and invalid/empty bytes causing `validationErrors`.

6. `src/lib/docx-writer.test.ts`
   - Tests full pipeline result includes contract/intermediate/adapterResult/review/record/bytes.
   - Tests known warnings produce `review.verdict === "warn"` and `record.status === "warning"`.
   - Tests injected validation errors produce `review.verdict === "fail"` and `record.status === "failed"`.
   - Tests no forbidden leakage keys and no `outputPath` for library-only bytes.

### Modify

1. `package.json`
   - Add `docx` under root `dependencies`.
   - Add `jszip` under root `dependencies` only if `src/lib/docx-package-probe.ts` needs it for product runtime probing.

2. `package-lock.json`
   - Update through package manager install so dependency graph is reproducible.

3. `src/test-helpers/docx-export-fixtures.ts`
   - Modify only if tests need a helper for alternate invalid/minimal fixture variants; do not add raw source leakage fields.

### Do Not Modify in Slice C

- `src/components/*`
- `src/stores/*`
- `src/commands/*`
- Tauri configuration or save commands
- Experiment adapter code as product source

## Executable Implementation Steps

1. **Lock the dependency decision**
   - Add root dependency `docx` at the version line proven by experiments (`^9.6.1` unless package resolution requires a compatible newer lockfile version).
   - If the product probe needs ZIP parsing, add `jszip` as root runtime dependency.
   - Commit/record dependency rationale in the ADR section above; do not add sidecar projects or manual-template assets.

2. **Add the product structural probe first**
   - Implement `src/lib/docx-package-probe.ts` with browser-safe input types.
   - Normalize probe failures into `validationErrors`; normalize known limitations into `knownWarnings`.
   - Add tests proving valid bytes pass and malformed bytes fail.

3. **Add the isolated `docx` adapter**
   - Implement `src/lib/docx-ts-adapter.ts` using only `DocxIntermediateDocument` input and simple style mappings.
   - Render all current block types: document title, headings, paragraphs, ordered/unordered lists, and simple tables.
   - Return browser-safe bytes and stable adapter metadata with `adapterId: "docx-npm.v1"`.

4. **Add the product writer orchestration**
   - Implement `src/lib/docx-writer.ts` to build the contract/intermediate, render bytes, run the product probe, call `reviewDocxExport`, and build `DocxExportRecord`.
   - Preserve all artifacts in the return value for auditability.
   - Do not set `outputPath` in Slice C unless a future caller actually writes a file.

5. **Add focused regression tests**
   - Adapter tests for generated bytes, stable id, supported block rendering, and warnings.
   - Probe tests for valid/invalid package behavior.
   - Writer tests for warn/success/fail record mapping, audit hashes, no leakage, and library-only no-outputPath behavior.

6. **Run required verification and fix until green**
   - `npm run typecheck`
   - `npx vitest run src/lib/docx-package-probe.test.ts src/lib/docx-ts-adapter.test.ts src/lib/docx-writer.test.ts src/lib/docx-export-contract.test.ts src/lib/docx-intermediate.test.ts src/lib/docx-match-review.test.ts src/lib/docx-export-record.test.ts`
   - `npm run build`

## Acceptance Criteria

- `docx` npm / `docx-npm.v1` is the selected Slice C adapter in code and ADR.
- Root dependencies are explicit and reproducible in `package.json` + `package-lock.json`; no sidecar runtime is added.
- `src/lib/docx-ts-adapter.ts` is the only product module importing `docx`.
- `src/lib/docx-package-probe.ts` is product code if writer uses it; any ZIP parser it imports is a runtime dependency.
- Product-facing byte output is `Uint8Array`, `ArrayBuffer`, or `Blob`; no product API requires Node `Buffer`.
- Product adapter/writer do not import `fs`, `path`, `child_process`, Tauri APIs, store modules, UI components, or experiment scripts.
- Writer returns contract, intermediate, adapter result, review, record, and bytes.
- Known limitations for manual Word openability and high-fidelity/style replica are warnings, not hidden claims.
- Adapter/probe validation errors become `docx-validation-error` blocking issues through `reviewDocxExport` and produce failed records.
- Known warnings become warning records, not false full-success records.
- No forbidden source leakage keys appear in contract, intermediate, adapter result, review, record, or test report objects.
- Generated DOCX bytes are non-empty and structurally probe as a DOCX package with required package entries.
- No UI/store/Tauri/export-button/save-flow files are changed.

## Risks and Mitigations

- **Risk: Adapter self-reporting hides invalid packages.** Mitigation: product `docx-package-probe.ts` is mandatory and feeds review validation errors.
- **Risk: Browser bundle fails due to dependency/node API usage.** Mitigation: require `npm run build` and forbid `Buffer`, `fs`, `path`, and `child_process` in product writer/adapter/probe.
- **Risk: Users infer high-fidelity Word output.** Mitigation: stable known warnings and no high-fidelity/manual-openability claims in names, records, or tests.
- **Risk: Sidecar becomes tempting for validation.** Mitigation: ADR rejects sidecar for MVP due to Slice B high packaging/runtime costs; keep adapter boundary swappable for future.
- **Risk: Scope creeps into UI/export button.** Mitigation: file exclusions and stop condition below.

## Stop Condition

Stop Slice C when the library writer can generate structurally probed DOCX bytes from the existing fixture, produce an auditable review/record path with warnings/failures correctly mapped, pass required typecheck/tests/build, and leave UI/store/Tauri/save-flow untouched. Do not continue into export-button UX, desktop file save, manual Word openability, or high-fidelity formatting work.
