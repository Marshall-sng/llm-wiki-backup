# RALPLAN-DR: Slice E1 DOCX High-Fidelity Baseline Diagnostics

Date: 2026-05-15
Scope: Planning only; no implementation in this artifact.

## Outcome

Establish a DOCX-only, non-blocking measurement baseline for high-fidelity export: source/exported style facts, reverse-probed exported DOCX facts, deterministic fidelity coverage buckets, and a gap report that guides E2 writer mapping without changing current DOCX export behavior.

## Evidence Grounding

Current DOCX MVP surfaces:
- `src/lib/docx-export-contract.ts` builds the DOCX export contract and guards against forbidden source leakage.
- `src/lib/docx-intermediate.ts` builds the intermediate document.
- `src/lib/docx-ts-adapter.ts` renders DOCX bytes with the current writer.
- `src/lib/docx-package-probe.ts` performs package/XML structural checks.
- `src/lib/docx-match-review.ts` turns adapter/probe validation into review verdicts.
- `src/lib/docx-export-record.ts` records export metadata/diagnostics.
- `src/lib/docx-writer.ts` currently flows contract -> intermediate -> render -> package probe -> review -> record.
- `src/lib/docx-export-save.ts` blocks save on failed review; E1 must not add fidelity gaps to blocking validation.
- Tests already exist for the DOCX surfaces plus `src/test-helpers/docx-export-fixtures.ts`.

Decision log grounding: `.omx/plans/requirements/migration-decision-log.md` Decision 041 splits high-fidelity DOCX into E1 diagnostics, E2 writer style mapping, and E3 UX/productization.

## RALPLAN-DR

### Principles

1. Measurement before mapping: E1 measures fidelity facts and gaps before changing writer style behavior.
2. Non-blocking by construction: fidelity gaps are diagnostics, not `validationErrors`, review blockers, save failures, or parity claims.
3. DOCX-first boundary: no XLSX/PPTX expansion and no generalized office-export abstraction in E1.
4. Evidence-backed claims only: XML/package probes can report observed facts, not Word/WPS visual parity or 100% fidelity.
5. Leakage-safe diagnostics: reports may include rule IDs, hashes, categories, and bounded evidence refs, but not raw source body text or raw evidence dumps.

### Decision Drivers

1. Preserve current export behavior proven by desktop smoke: DOCX export should still succeed with existing boundary reminders.
2. Create actionable E2 input: identify which style dimensions are restored, partial, missing, or unverified.
3. Keep blast radius low: isolate diagnostics from writer, review blocking, save flow, and UI productization.

### Viable Options

#### Option A — Recommended: separate diagnostics module after render/probe

Add `src/lib/docx-fidelity-diagnostics.ts` and tests. It reads available source-side rule inventory from `formatProfileSnapshot.formatSpec.rules`/`FormatSpecRule.attributes` plus exported DOCX XML facts from rendered bytes. Full `StyleFactsEnvelope` is not assumed to exist on `DraftProcessingFormatProfileSnapshot`; E1 may accept an explicit optional `sourceStyleFacts` input, but absent facts must be marked `unverified`. `writeDocxExport` may return `fidelityDiagnostics` as an extra non-blocking field after current render/probe, but must not merge it into adapter validation, review blocking, record diagnostics, save status, or generated bytes.

Pros:
- Cleanly separates measurement from validation and writing.
- Gives E2 a stable report shape without risking current export success.
- Avoids overloading `docx-package-probe` structural assertions.

Cons:
- Some XML parsing may overlap with package probe until shared helpers are extracted later.
- If `WriteDocxExportResult` exposes the report, tests must lock that it remains non-blocking.

#### Option B — Extend `docx-package-probe`

Add style/fidelity facts directly to `probeDocxPackage` output.

Pros:
- Reuses current DOCX zip/XML seam.
- Minimal new module count.

Cons:
- Probe results are currently merged into `adapterResult.validationErrors` / `knownWarnings`; fidelity gaps could accidentally become blockers.
- Conflates structural validity with high-fidelity measurement.

Use only for shared XML extraction helpers, not as the main E1 diagnostics API.

#### Option C — Embed gaps in `docx-match-review` / export record

Treat fidelity coverage as part of review or persisted record diagnostics.

Pros:
- Makes diagnostics visible in the existing export audit trail.
- Easier future E3 user-facing path.

Cons:
- High risk of changing review verdict semantics or UI claims too early.
- Record schema churn before report shape is proven.

Defer persistent/user-facing integration to E3 unless implementation can prove zero behavior change.

#### Option D — Start E2 writer style fixes now

Change `docx-ts-adapter.ts` styles for fonts, margins, headings, numbering, and tables.

Pros:
- May improve output immediately.

Cons:
- Violates E1-before-E2 sequencing.
- Makes failures hard to attribute because measurement and mapping change together.

Rejected for E1.

### Recommended Decision

Implement Option A: a DOCX-only, versioned, JSON-safe `docx-fidelity-diagnostics` report generated after current DOCX rendering and structural probing. Expose it only as a non-blocking execution artifact, preferably `WriteDocxExportResult.fidelityDiagnostics`, with explicit tests proving it does not affect bytes, adapter validation, review verdict, record status, or save behavior.

## Proposed Diagnostics Contract

New module/touchpoint:
- `src/lib/docx-fidelity-diagnostics.ts`
- `src/lib/docx-fidelity-diagnostics.test.ts`
- Optional minimal touch: `src/lib/docx-writer.ts` adds `fidelityDiagnostics` to `WriteDocxExportResult` after render/probe.
- Optional fixture updates: `src/test-helpers/docx-export-fixtures.ts` only if richer style rules are needed.

Report fields:
- `schemaVersion`: e.g. `docx-fidelity-diagnostics.v0`.
- `sourceInventory`: rule IDs, targets, priorities/confidence, evidence refs, and availability state derived primarily from `formatProfileSnapshot.formatSpec.rules` and `FormatSpecRule.attributes`; do not claim full source style facts unless an explicit optional `sourceStyleFacts` input is provided. Missing source facts must become `unverified`, not guessed.
- `exportedFacts`: bounded facts observed from `word/document.xml`, `word/styles.xml`, `word/numbering.xml`, and package parts.
- `coverage`: array keyed by rule/style dimension with bucket `restored | partial | missing | unverified`.
- `gaps`: deterministic gap list for E2, with target, source rule ref, exported evidence ref, and reason.
- `limitations`: includes `notWordWpsParityValidated: true`, `noManualTemplateRoute: true`, and `notFullFidelityClaim: true`.

Coverage bucket semantics:
- `restored`: expected rule/dimension has matching exported XML evidence from the relevant part.
- `partial`: some matching evidence exists but key dimensions are absent or only approximated.
- `missing`: source rule/dimension is known and no exported evidence is found.
- `unverified`: source fact is unavailable or XML/package evidence cannot prove the dimension.

Initial dimensions should stay bounded to current MVP blocks: document title, headings, body paragraphs, ordered/unordered lists, table structure, font/style evidence, margins/spacing if observable. Do not add visual rendering comparison.



### Architect iteration fixes incorporated

- Source expectations come from original `formatProfileSnapshot.formatSpec.rules` and their `attributes`; E1 must not rely on `contract.formatRules` alone because the current contract mapping drops attributes.
- Full `StyleFactsEnvelope` is not assumed on `DraftProcessingFormatProfileSnapshot`; if future callers provide `sourceStyleFacts`, it must be an explicit optional input.
- Missing source facts are classified as `unverified`, not `missing` or `failed`.
- Fidelity gaps must never be merged into `adapterResult.validationErrors`, `adapterResult.knownWarnings`, review blockers, or save failure state in E1.
- Reports must not persist raw `document.xml`, `styles.xml`, source body text, or raw evidence dumps; store normalized facts, counts, hashes, assertion IDs, rule refs, and gap codes only.

## Acceptance Criteria

1. E1 produces a versioned, JSON-serializable DOCX fidelity diagnostics report for existing DOCX export fixtures.
2. Diagnostics distinguish source rule inventory from actual source style facts; unavailable facts are marked `unverified`, not guessed.
3. Coverage buckets are deterministic and tested for at least restored/partial/missing/unverified cases.
4. Fidelity gaps are not added to `adapterResult.validationErrors`, `adapterResult.knownWarnings`, `review.blockingIssues`, `review.warnings`, save failure state, or current product copy.
5. Current DOCX writer output bytes are unchanged for the same input, or any byte difference is explained solely by unavoidable timestamp/export-id inputs already controlled in tests.
6. Existing DOCX export behavior remains: desktop-style export can succeed with current boundary reminders; no auto-overwrite, no manual template route, no Word/WPS parity claim.
7. Tests cover leakage safety: diagnostics do not include forbidden raw source/evidence keys from `FORBIDDEN_DOCX_EXPORT_LEAKAGE_KEYS`.
8. No XLSX/PPTX files, generic office abstractions, or UI productization are introduced.

## Verification Plan

Unit tests:
- `docx-fidelity-diagnostics.test.ts`: schema/version, JSON serialization, bucket classification, source inventory handling, leakage guard, and limitation flags.
- Package/XML fact extraction tests using existing fixture-generated DOCX bytes and controlled synthetic XML where needed.

Integration tests:
- `docx-writer.test.ts`: if `fidelityDiagnostics` is returned, assert it is present after render/probe and does not alter `adapterResult.validationErrors`, review verdict, record status, or bytes.
- Existing `docx-package-probe.test.ts`, `docx-match-review.test.ts`, `docx-export-record.test.ts`, and `docx-export-save.test.ts` continue passing unchanged unless assertions are added to prove non-blocking behavior.

Save-flow regression:
- Confirm warning/pass/fail/cancel semantics in `docx-export-save.ts` remain driven by existing review/save rules, not fidelity coverage gaps.

Commands:
- `npm run test:mocks -- src/lib/docx-fidelity-diagnostics.test.ts src/lib/docx-writer.test.ts src/lib/docx-export-save.test.ts`
- `npm run typecheck`
- If test runner path filtering is unsupported, run `npm run test:mocks`.

Manual smoke (optional, not acceptance for parity):
- Export DOCX from Drafts UI and verify it still succeeds with existing boundary reminders. Do not record this as Word/WPS parity proof.

## Pre-mortem Risks

1. Diagnostics become a hidden gate: mitigated by tests proving gaps do not enter validation/review/save blockers.
2. Bucket labels imply stronger fidelity than proven: mitigated by `limitations` and `unverified` semantics.
3. Raw source/evidence leakage: mitigated by key denylist tests and source inventory-only design.
4. Brittle XML parsing: mitigated by bounded dimensions and tests against generated fixtures rather than exact full-byte snapshots.
5. Scope drift into E2: mitigated by explicit no changes to `docx-ts-adapter.ts` style mapping except test-only observation if unavoidable.
6. Scope drift into E3: mitigated by no Drafts UI copy or productization changes in E1.

## Out of Scope / Deferred

Defer to E2:
- Writer mapping for fonts, sizes, paragraph spacing, margins, numbering formats, table borders, style IDs, section/page setup.
- Any attempt to improve actual generated DOCX fidelity beyond preserving current behavior.

Defer to E3:
- User-facing fidelity dashboards, polished warnings, export-history UX, replacement of raw boundary codes, and product copy changes.

Out of scope entirely for E1:
- Manual template import/route.
- Auto-overwrite behavior.
- Word/WPS visual parity claims or screenshot comparison.
- XLSX/PPTX export or generalized office-fidelity framework.
- Source extraction overhaul or raw source body/evidence dump in diagnostics.

## ADR

Decision: Build a standalone, non-blocking DOCX fidelity diagnostics report before any writer fidelity changes.

Drivers: preserve current export behavior; create actionable measurement for E2; avoid unsupported fidelity/parity claims.

Alternatives considered: extending package probe, embedding in review/record, starting writer fixes now.

Why chosen: Option A gives the clearest measurement boundary and lowest regression risk while producing concrete E2 inputs.

Consequences: E1 may expose gaps without improving fidelity yet; E2 must consume the report to prioritize writer mapping; E3 must later translate diagnostics into user-facing UX.

Follow-ups: E2 writer mapping plan should rank gaps by coverage report severity/frequency; E3 UX plan should replace boundary reminders only after diagnostics are stable.

Available agent types: explore, planner, architect, debugger, executor, test-automator, test-engineer, verifier, code-reviewer, critic, writer.

Suggested reasoning: executor medium; test-automator medium; verifier high; code-reviewer high.

Goal-mode follow-up: `$ultragoal` is suitable if E1/E2/E3 should be tracked as durable sequential goals; keep `$performance-goal` and `$autoresearch-goal` unused because this is not primarily performance or external research.

## Stop Condition

Stop E1 when tests prove a versioned diagnostics report can measure exported DOCX style/coverage gaps from current fixtures without changing generated writer behavior, review/save semantics, product claims, or DOCX-first scope. Do not proceed to E2 writer mapping until this baseline is merged and verified.
